## S03：已有结果

使用确定性合成文件、网页与工作区记录，覆盖中文单字/双字、混合文本、路径/URL、类型、工作区范围、同名未授权项、字面百分号/下划线/引号、Unicode 归一化和无匹配。每规模先运行 19 查询 × 2 策略的全量参照比对，四种规模共 152 组，结果一致。精确名排序与静态撤权过滤检查也通过。

各规模每策略为 570 次交错热查询；每一具体查询仅 30 次，不能把单查询 P99 视为稳定估计。

| 资源数 | 短词扫描基线 P95 | 加入短词索引 P95 | 两种索引建完后的 SQLite 分配页体积 |
|---|---:|---:|---:|
| 10,000 | 2.327 ms | 2.343 ms | 4.50 MiB |
| 50,000 | 11.599 ms | 11.561 ms | 21.35 MiB |
| 100,000 | 23.525 ms | 23.525 ms | 42.38 MiB |
| 500,000 | 118.551 ms | 118.792 ms | 190.40 MiB |

该体积是内存 SQLite 的已分配页，包含基础数据、两个索引及空闲页。两种策略在同一个库中比较；不能据此比较两份独立产品的 RSS 或推算索引净体积。

10 万资源下，具体查询的 P95：

| 查询 | 短词扫描基线 | 加入短词索引 |
|---|---:|---:|
| 张 | 14.894 ms | 3.762 ms |
| 张三 | 14.440 ms | 3.833 ms |
| 合同 | 13.970 ms | 2.847 ms |
| 项目 A（高命中路径） | 24.264 ms | 24.217 ms |

查询计划显示，短词基线为 `SCAN r`，候选走 FTS MATCH 的 posting 检索；两者都出现用于最终排序的临时 B-tree。高命中路径查询没有从短词索引获益，主导了混合负载的尾部耗时。索引降低部分查询的候选量，不会自然消除所有匹配项的核对和排序成本。

10 万记录的 trigram 构建约 0.57 秒，附加短词 token/索引构建约 6.86 秒；50 万分别约 3.41 秒与 32.28 秒。数字包含当前 Python 实现及 SQLite 的工作，不能作为 Rust 原生扫描或真实目录索引吞吐。

**判断**：SQLite 路线值得继续验证；应用预生成短词 token 的方案改善了目标中文短词，无须立即换搜索引擎。它仍是候选方案。后续需要验证真实路径分布、索引增量成本、高命中查询排序及实际打包版本。

### 磁盘与并发写入补充实验

在已确认的样本目录创建 10 万资源的合成 SQLite 数据库，使用 WAL、`synchronous=FULL`，分别执行 570 次无写入查询和 570 次并发写入查询。两轮均使用短词索引方案及同一查询顺序。

| 条件 | P50 | P95 | P99 | 查询错误 |
|---|---:|---:|---:|---:|
| 无后台写入 | 4.426 ms | 25.405 ms | 26.208 ms | 0 |
| 后台小事务写入 | 4.639 ms | 26.113 ms | 26.983 ms | 0 |

并发期间完成 203 个事务、2,030 次合成资源更新，业务元数据及两个 FTS 索引同事务更新；写入错误为 0。停止写入后，19 类查询与当前业务行的独立参照结果一致。

这提供了本机 SQLite 在磁盘与持续小事务下的初步证据。数据库刚生成，OS 缓存已被预热，不是冷缓存实验；写入也不是操作系统扫描器或真实文件通知。不能用这一结果推断所有写入量、大事务或目标硬件均满足预算。

**尚未完成**：真实冷热对照、取消/分页、Rust Core、分组 Top-N、IPC 和真实 UI 可见时延，以及 Windows 同条件实验。内核结果不等于达到 150 ms 的用户输入到首批结果可见目标。

## S02：已有结果

对工作区内两份已有源码/文档进行了只读元数据探测，没有生成可变更文件样本或修改文件内容：

| 项目 | 本轮观察 |
|---|---|
| 卷格式 | APFS (Encrypted) |
| 普通 Bookmark 创建与立即解析 | 两个文件均成功，返回原路径，stale=false |
| Document ID | 两个文件在创建 Bookmark 前后均未返回值；刷新 URL 缓存后仍不可用 |
| 内容未改动 | 探测前后 SHA256 相同 |
| 不安全 fixture 根输入 | `/`、`/private/tmp` 本身、当前工作目录均被拒绝，3/3 |

**判断**：Bookmark 的基本 API 可在当前命令行环境调用。Document ID 必须按可选证据处理，不能只引用官方 safe-save 说明就把它列成本机必然可用的身份层。

这不能单独证明 APFS 普遍不支持 Document ID，也不能确定缺值来自文件状态、平台实现或当前运行环境中的哪一项。

### 原生文件变更与新进程解析

随后在确认过的目录内生成独立文本样本，执行七类 API 操作。操作错误为 0；下表的“新进程解析”仅指 Bookmark 返回目标路径且内容摘要与该操作后的文件相同，不代表允许旧业务资源自动绑定。

| 操作 | 原件 inode | 新进程 Bookmark 解析 | 身份解释 |
|---|---|---|---|
| 原地写入 | 不变 | 成功，stale=false | 当前物理对象连续 |
| 改名 | 不变 | 成功，stale=true | 找回新路径，物理对象连续 |
| 同卷移动 | 不变 | 成功，stale=true | 找回新路径，物理对象连续 |
| Data 原子写入 | 改变 | 成功，stale=true | 已找回保存后的文件，仍需区分替换身份 |
| FileManager 替换 | 改变 | 成功，stale=true | 已找回替换后的文件，仍需区分替换身份 |
| 复制 | 原件不变，副本不同 | 仍解析到原件 | 没有自动改指副本 |
| 删除后同名重建 | 改变 | 同样成功，stale=true | **负例：返回的是新对象，不能据此继承旧业务关系** |

这些样本的 Document ID 均未返回值。新增证据表明：Bookmark 确实能在本机恢复两种安全替换 API 的路径，但它也会解析到删除后同名新建的对象。`stale` 和“路径可打开”均不足以区分二者；nil Document ID 也不能作为相等证据。

因此不能用“七种操作均解析到文件”宣称严格身份追踪全部通过。原生方案具备定位收益，安全保存与任意同路径替换的区分仍未闭合；不能据此降低 PRD 的防误连要求。真实 WPS/Word 保存、系统重启、跨卷、授权撤销和正式签名包尚未验证。

首次实际启动还发现了样本目录校验缺陷：Foundation 将存在的 `/private/tmp` 表示成 `/tmp`，但未创建的子路径仍保留 `/private/tmp`，使合法目录被拒绝。该次未生成样本；已改用 POSIX 真实路径与父目录校验，随后实际正例运行成功，根目录/临时目录本身/代码目录仍被拒绝。之前只测拒绝输入不足以证明合法输入可运行。

WPS UI 尝试后仍停留在首页，新建按钮和快捷键未带来可观察的空白文档；菜单已关闭并恢复首页。该现象仅说明当前自动控制未完成创建，不能判定 WPS 本身不能新建；没有操作任何已有办公文件。
