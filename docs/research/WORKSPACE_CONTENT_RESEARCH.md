# 工作区非文件内容调研与 V1 建议

调研日期：2026-11-19。范围：行政、HR、运营、文案围绕“一件正在处理的工作”保存哪些内容。本文为建议，不代表已实现、用户价值已证实或 V1 自动扩容；未改主 PRD 或业务代码。

**推荐最小组合：文件引用 + 好用的网页引用 + 可选的工作区简短说明。** 前两项已属 V1，网页自动标题是用户本轮明确要求；工作区说明是唯一值得考虑纳入本次交付的新增候选。结构化联系人、清单引擎、独立笔记、任务/提醒、会议记录均建议留到真实用户验证后。若核心拖拽、文件连续性、原生验收仍未通过，说明也应后移，不能占用交付关口。

## 1. 已确认事实与约束

本地核查位置：`PRD.md` 的定位、工作区、V1 排除项；`ARCHITECTURE.md` 的事实源/模型；`crates/worktwill-core/src/model.rs`、`schema.sql`。

- WorkTwill 当前目标是快速取回与组织已有资料；不是新建另一套办公数据平台。工作区目前是扁平的虚拟上下文，混合 `file`/`web`。
- 正式 `resources.kind` 的 SQLite CHECK 仅允许 `file/web`；`Workspace` DTO 仅有 id、name、count。现在没有 note/person/task 模型。新增一个卡片外观不等于新增内容类型成本低。
- Rust/SQLite 是业务事实源；关系、备份恢复、搜索投影、撤权和活动都已有消费者。React 不应另存非文件正文到 localStorage。
- 旧 PRD 明确排除了自动创建个人笔记、任务、工作日志、自定义 widget 等；用户本轮授权“研究工作区还能装什么”是研究授权，不应解释成这些全部自动进入 V1。
- 用户本轮明确批准日历维度的文件时间线。它是已观察资料的回顾入口，不等于承诺排期、截止日、提醒或待办日历。
- 尚无本项目真实访谈、付费或持续使用数据。下面的人群收益都是需要验证的场景假设。

## 4. 推荐的工作区呈现

工作区首先应回答“这件事是什么、现在有哪些资料、最常用入口在哪、最近发生了什么”。建议基于现有模型分成下面三个自然层次，不新增 widget 配置器：

1. **标题区**：工作区名称；若采纳说明，显示 1–3 行可展开的纯文本说明；空说明不预留大块空白，不强迫填写。
2. **资料区**：沿用统一 file/web 列表与筛选、拖入、加入/移除/引用转移；网页显示可编辑标题和可识别域名。URL 能作为 HR/采购/运营/文案业务入口，不要另建“快捷方式”资源表。
3. **文件变化入口**：进入当前工作区范围的日历时间线；展示“文件修改时间”“首次发现/首次加入”的真实事实并标明来源。不要把工作区改名等管理事件挤到用户的主要变化流。

“高级感”可以通过字号层级、留白、稳定栅格、少量强调色、清晰文件类型与低噪声操作实现；添加更多卡片或花哨封面不会自动提高办公效率。用户参考图的价值在日历定位、按日事件分组、可解释来源及打开/定位操作，应保留这些信息结构，并适配最小窗口，避免三列挤压文件名。

## 5. 若本轮采纳工作区说明，最小完整实现契约

以下为实施建议，主 agent 应据最终范围更新 PRD/架构与验收；本次调研未实施。

### 状态归属

- 文本是 `Workspace` 元数据，例如 `description`，不创建独立 `note` 资源，不进入文件目录或 sidecar。
- Rust WorkspaceService/Store 管理唯一持久数据；React 仅管理当前草稿和保存状态。建议显式“保存/取消”，保存失败保留输入，不用前端延时写入掩盖失败。
- 使用版本化 migration 增加非空默认空字符串字段。旧库打开后已有工作区、UUID、关联和 URL 保留；DTO 从 Rust 重新生成。
- 更新工作区的命令与既有 operation receipt 契约复用；保存/修改与回执同事务。不要单独开 localStorage 或 JSON 文件。
- 工作区读取、备份/恢复、删除、未来导出均由原来的所有者处理；不赋予文件权限，撤权文件仍匿名，说明不得自动回填被撤权文件名/路径。
- 默认不把说明正文纳入全局搜索；全局搜索仍按当前资源/工作区名契约工作。若需要正文命中，先明确“搜索范围包含用户所写说明”，另补索引正确性与排序验收。

### 内容和交互边界

- 建议 2,000 个 Unicode 标量上限，采用多行纯文本，保存成功后按换行渲染；上限是待采纳产品建议，不是已批准数值。
- 不解释 Markdown/HTML，不执行内嵌链接/脚本；没有富文本工具条、图片附件、表格、任务状态、提醒、分享或协作。
- 用户可写“联系小李确认预算”等普通上下文。不能把这句话自动解析为联系人、待办或未来 Agent 指令。
- 删除工作区同时删除它的说明，确认文案必须覆盖说明会丢失；源文件/网页其他工作区引用仍保留。由于现有删除确认主旨是“仅移除引用”，若添加本地正文，原确认语义需要同步修正。
- 不把每次编辑说明写进默认文件时间线；可保留必要技术活动，但不要混淆为文件修改。

### 最低验收

| 场景 | 必须观察到的结果 |
|---|---|
| 空说明、仅空格、中文/英文/emoji、多行、长度边界 | 保存规则明确；显示不溢出；不破坏工作区名、资料和布局 |
| 编辑后取消、切区、关闭弹窗 | 草稿行为明确；未保存内容不静默变成已保存 |
| 后端写入失败、重复点击、命令重放 | 草稿保留、错误可见；无重复事件或重复副作用 |
| 保存后退出重启 | 文本与工作区 UUID、关联一致；不依赖浏览器缓存 |
| 备份→修改→恢复 | 按恢复点恢复说明，文件权限仍按恢复策略重授权 |
| 旧 schema 升级、未来 schema 拒绝 | 现有数据无损；失败不进入半迁移状态 |
| 删除工作区 | 说明按确认删除；源文件字节/大小/mtime 与其他区关系无变化 |
| `<script>`/HTML、超长文本、特殊 Unicode | 显示为文字，不执行；长度与输入法行为正确 |
| 900px 最小窗口、英文、长名、说明展开 | 操作入口可见；列表仍可读，无水平遮挡 |

如果不能完成这些，宁可只交付完善的 file/web 工作区，而非放一个会丢内容的便签框。

## 6. 明确不从本次调研推出的结论

- 不宣称非文件内容已验证高频、会提高留存或能收费。
- 不因此新增 HR/员工档案、CRM、岗位数据库和自动清单模板。
- 不把工作区说明演进成随处创建的笔记、每日笔记、知识图谱、通用属性系统或块编辑器。
- 不将竞品 GPL 代码或其文字/图标/视觉素材直接复制进本项目；本次是功能模式研究，许可证与商业化决定仍未定。
- 不把外部网页请求扩展为下载正文、截图、登录、读取用户浏览器 cookie、监听页面访问或保存页面副本。

## 7. 建议怎样验证是否继续扩展

在本轮可靠交付后，用 5–8 位目标用户的同一个实际任务验证：他/她在工作区以外还要打开什么，为什么要离开，明天回来最容易忘掉什么。让其先用 file/web，再试一句工作说明；记录是否自发填写、是否在再次取回时读取、是否减少查找或反复问人。

只有当多位用户持续遇到同类缺口时再决定：反复只需解释资料→说明；需要记住流程核对→轻量清单；需要按人追踪跨工作事项→人员模型；需要日程执行→任务系统。不要把这四类需求用一个“万能卡片”提前合并。

本次建议的商业假设是“降低取回与恢复上下文的成本”，不是“拥有更多对象类型”。官方维护、稳定发行和支持服务可能成为交付价值，但本次未确认收费形式、价格或许可方案。

### 已定位的具体问题与补测建议

1. **扫描轮询会重复追加已加载的分页。** `desktop/src/App.tsx:74` 只要 `offset>0` 就把响应 append 到旧列表；`:80–83` 在扫描 running 时每1.2秒改变 refresh。用户加载第2页后，轮询重取同一 offset 会把同一批资料再次追加。建议区分“分页推进”和“进度刷新”，或从稳定 revision/cursor重建列表；不可只靠渲染 key去重掩盖漏页。补测：120条以上资料、running、加载更多后跨两次轮询，资源id数量与去重数量一致。
2. **退出添加搜索后，普通快捷键搜索可能仍执行加入。** `App.tsx:110` 点击外部只关闭 searchOpen，不清理 addIntent；`:106–107` Cmd/Ctrl+K重新打开也不重设模式；`:132` 会继续走 Link。建议明确“添加文件”模式退出规则，普通快捷键恢复普通全局搜索，保留查询并不等于保留动作意图。补测：工作区添加文件→点击外部→快捷键搜索→Enter，应该打开而不是隐式增加关系。
3. **单文件授权缺少完整观察与管理闭环。** 新 `ingest.rs` 已建立 file_grants，但 `scan_all`、原生 `start_watcher` 在审读时仍仅遍历目录 roots；独立授权且不在任何目录根内的文件修改不会被现有重扫更新，新时间线会漏掉这类文件。且 `Mutation` 尚无单文件撤权入口。建议作为拖拽功能的一部分同时实现受控文件复验、独立撤权和搜索/活动的权限并集。不要通过暗中授权父目录解决。
4. **独立单文件引用的修复仍依赖目录授权。** `store.rs` 的 `relink` 在事务内只允许 `path_allowed`，与 `resolve_resource` 已纳入 file_grants的逻辑不一致。授权单文件后原件位置改变，用户通过原生选择器选择目标仍可能被要求授权整个位置。应设计“重新指向并明确授权所选文件”或复用有界 native import授权逻辑，不能扩大目录，也不能直接信任前端路径。
5. **常见同路径替换的手动修复会与已扫描新对象冲突。** `relink` 检测其他资源已有同 identity时返回 conflict；扫描发现新对象通常已经为它创建独立资源。此时旧关系虽保留，却没有可完成的合并确认路径，用户可能只能逐区重加。验收文档已承认该缺口，应补“用户确认合并目标资源→事务迁移全部关系/收藏→不伪造历史事件→重试幂等”的验收，不将可见的“重新指向”按钮当作实际可修复。
6. **当前搜索无法告诉用户还有更多结果。** `Store::search` 固定Top30，返回 `has_more:false`；当前前端没有完整结果入口。分组视觉已实现，但不能因此把F03全量结果/筛选排序登记完成。应至少按最终契约实现真实has_more和明确的完整结果路径，补31+项命中、多种资源竞争名额、过滤和分页的正确性。
7. **新活动数据尚未贯穿目录扫描。** 审读时 ingest 已插入 file_discovered，migration已添加source/file_modified_at；`catalog.rs:193–215` 普通目录扫描仍只更新资源和搜索，未写首次发现/mtime变化。日历若只消费当前 activities，会使“拖入文件有事件，目录扫描文件无事件”。这是正在实施项，不是已有功能回归；应在 Catalog 的唯一归一事务里补事件去重，并用同一事实源查询月聚合/按日明细。

建议先处理1–4并覆盖回归，再以5–7等完整范围逐项验收。这里没有复跑性能基准；记录中的Rust查询预算通过仅覆盖其明确测量负载，不能替代原生可见延迟与持续扫描压力。
