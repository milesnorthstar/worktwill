# V1 时间线与工作台交互复核

复核日期：2026-11-19。范围为正式入口 `desktop/src/App.tsx`、`workbench/components.tsx`、`workbench/useResourceDrag.ts`、`timeline/ActivityTimeline.tsx` 及对应 CSS；保留原型不属于本次验收对象。

这是独立源码复核，供当前迭代修复和回归使用，不代表实际桌面视觉验收。根任务负责原生运行、截图与真实交互检查；以下问题的状态以本次复核时的源码为准，修复后仍需按触发步骤回归。

## 当前设计判断

顶部统一导航、左侧月历与筛选、中部按日时间线、右侧快速返回符合用户参考图的信息关系。默认时间线优先文件修改、首次发现与应用内打开，将工作区管理放到单独筛选，能够减少管理噪音。卡片区分文件修改时间和本应用发现时间，首次发现不冒充创建历史；这些语义应保留。

V1 最应补齐的是首次进入的下一步、筛选为空的解释、搜索与新增网页的目标一致性，以及取消拖拽的可靠性。无需为此再建立新的状态层或扩展时间线功能。

## 影响完整流程的待修项

### 1. 默认动态页的首次启动缺少直接收纳入口

- 源码：`App.tsx` 默认 `initialView='activity'`；`ActivityTimeline.tsx` 的空记录区域只建议更换日期和筛选。
- 触发：全新资料库首次启动，尚未授权任何管理位置、也没有工作区。
- 影响：用户看到完整月历，却没有明显的“添加管理位置”下一步。右上设置图标可以找到授权设置，但默认页未把它与开始使用联系起来。
- 最小修法：父页面根据真实授权状态提供首次使用入口，或向时间线传入受控授权回调。仅在确实没有已授权文件来源时出现；已有授权但所选日期为空时仍保留日期空态。
- 回归：新库首屏可直接发起原生位置选择；取消选择无假记录；授权成功后出现真实首次发现；切换无记录日期不重新变成新手引导。

### 2. 搜索和类型过滤为空时，不能沿用全资料空态

- 源码：`workbench/components.tsx` 的 `EmptyState` 只判断工作区、收藏、最近使用和管理位置，未区分 `view==='search'` 或工作区类型筛选。
- 触发 A：完整搜索页输入无匹配关键词。
- 影响 A：出现“扫描期间资料会逐步出现”或添加管理位置入口，用户无法知道搜索已完成且没有匹配。
- 触发 B：工作区实际有文件，切到网页分类，但没有网页。
- 影响 B：显示“这个工作区还没有资料”，把分类为空误说成整个工作区为空，主按钮还始终是添加文件。
- 最小修法：复用同一空态组件，按查询和当前 `kind` 选择准确文案及相关操作，不增加新状态源。
- 回归：全局搜索零结果显示“没有匹配资料”；工作区网页为空显示网页语义；收藏零结果保留收藏提示；加载中不先闪现错误空态。

### 3. 完整搜索中保留的工作区范围会进入新增网页目标

- 源码：`App.tsx` 的“查看全部搜索结果”直接 `setView('search')`，保留 `workspace`；`FormDialog source={workspace}`；新增网页提交将 `source` 作为 `workspace_id`。
- 触发：进入工作区 A，搜索后点击查看全部结果，再在完整搜索页新增网页。
- 影响：新增网页可能自动关联 A，尽管当前页面和网页表单没有显示这个目标。普通 `navigate()` 已清除工作区，因此该风险主要来自完整搜索的直接视图切换。
- 最小修法：新增网页关联目标以可见上下文为准，例如仅在 `view==='workspace'` 时传入 `source`。完整搜索可以保留原工作区筛选，但不能隐含复用它作为写入目标。
- 回归：工作区 A 内新增网页关联 A；工作区 A 进入完整搜索后新增网页不默默关联 A；编辑既有网页不改变其关联。

### 4. 完整搜索范围变化需要触发完整列表重读

- 源码：`App.tsx` 的资源读取 effect 调用 `searchPage` 时使用 `searchScope`，但依赖列表未包含该值；搜索浮层读取 effect 已包含它。
- 触发：停留完整搜索页，打开搜索浮层，在全部和当前工作区之间切换范围，随后关闭浮层。
- 影响：浮层与完整列表可能展示不同范围；用户看到范围已变，但下方结果仍是旧范围。
- 最小修法：搜索范围参与完整列表失效，并在范围变化时重置分页；不修改 Rust 事实源或搜索 API。
- 回归：完整页切换全部/当前工作区，两处结果一致；位于后续分页时切范围回到第一页；快速往返切换不让旧响应覆盖。

本轮复核 App、时间线、Catalog/导入/授权解析及原生拖放路径，只读检查业务实现。前述首次授权入口、准确空态、网页目标脱钩、完整搜索范围刷新，以及清选择名称、零结果方向键、模态快捷键均已见对应修复；不再将旧条目视为未修复缺陷。根任务报告的 UI/core 测试通过属于其运行结果，本独立复核没有重复运行，也不据此声称覆盖下列时序。

### P1：原生拖入在后台身份捕获完成后才按旧坐标确定目标

**源码路径**：`src-tauri/src/main.rs` 的 `DragDropEvent::Drop` 先保留 token 和原坐标，再在 `spawn_blocking` 中执行 `capture_import_selections`；捕获完成后才发 `files-dropped`。`desktop/src/App.tsx` 收到该事件时，用当时的 `document.elementFromPoint(x/dpr,y/dpr)` 或 `currentDropWorkspace.current` 选择目标。`DropInbox::begin` 仅锁定第一次调用时收到的目标，不能修复第一次已经选错的问题。

**触发**：在工作区 A 松手拖入大量文件或慢盘文件；后台还在逐个读取身份时，切到工作区 B，或在工作区网格滚动。捕获完成后，旧坐标可能对应 B/其他卡片，fallback 也已是 B。最终文件关联的是回包时目标，而非松手时目标。该竞态不依赖任意路径授权，受影响的是用户明确选择的关联目标，原文件不会因此被移动。

**最小正确方向**：松手时立即发出 token 与坐标的开始通知，在前端当时固定目标 UUID；身份捕获完成后只按同一个 token 继续。也可以在上下文发生变化时明确拒绝并要求重新拖入，但不能静默以新视图决定目标。目标删除仍由 Rust 提交时校验。

**必要回归**：人为延迟身份捕获，在 A 松手后切 B/滚动/删除 A；只能仍加入明确的 A，或显示目标失效，不得加入 B。接着发起第二次拖入，旧捕获完成不得覆盖新会话。仅发送已经准备好的 `files-dropped` 的现有 UI mock 无法覆盖此前的延迟阶段。

**证据级别**：源码确定的异步时序缺口；本独立复核未运行真实慢盘复现。

### P2：重载期间暂时清空 overview 会重置时间线工作区筛选

**源码路径**：App `reload()` 先 `setOverview(null)`，动态页向 `ActivityTimeline` 传 `overview?.workspaces ?? []`；时间线 effect 在所选 UUID 不属于传入列表时立即 `setWorkspaceId(null)`，将“元数据正在重读”当成“工作区已删除”。

**触发**：时间线选择工作区 A 后点击打开文件。`run()` 成功和原生 `catalog-changed` 都会重载，暂时传空列表，筛选因此变成全部工作区。后台扫描发通知也能触发相同结果。

**影响**：用户查看的范围会在正常操作后被扩大；这不是授权越界，Rust 仍执行授权过滤，但会破坏按工作区回顾的连续性。

**最小正确方向**：保留已知工作区元数据直到新快照到达，或显式告诉受控时间线工作区列表尚未加载，仅在确实加载成功且目标不存在时清掉筛选。无需新增第二套工作区 store。

**必要回归**：选择 A→打开文件→触发重载，完成后仍选 A；重载期间显示加载态而不扩大范围；真正删除 A 后才清理筛选。

**证据级别**：源码确定的父子状态路径；待根任务补集成回归。

## 迭代 004：搜索取消、分类席位和分类跳转独立复核

日期：2026-11-20。本轮只读检查 `desktop/src/api.ts`、App 两条搜索 effect、SearchPanel、`src-tauri/src/search_requests.rs` 与原生命令、core `cancellation.rs/search.rs/store.rs`。没有改业务代码，没有运行构建、测试、性能基准或其他 CPU 任务；完整检查与基准由根任务统一执行。

### P2：分类跳转只滚动，下一次 Enter 仍可能打开其他分类

**源码路径**：SearchPanel 分类按钮的 `onMouseDown` 阻止默认聚焦，保持焦点在搜索输入；`onClick` 仅将 `search-group-*` 滚入视口，没有调用 `onActive`。App 的 Enter 逻辑继续使用原 `active`，若是 -1 则打开 `results[0]`。

**触发**：搜索返回工作区/文件/网页混合结果，当前 active=-1；点击“跳到网页结果”，视口已经滚到网页组，接着按 Enter。输入仍有焦点，因此 App 会打开首个工作区/文件，而不是眼前网页。如果此前已通过方向键选过文件，跳到网页后同样仍可能打开已经滚走的旧文件。

**最小正确方向**：分类跳转同时把受控 active 设为该组首条结果的全局索引，再使用现有滚动逻辑；不要为此过滤掉其他组或改变后端席位。保留输入焦点是合理的，但可见高亮与 Enter 目标要一致。

**必要回归**：混合结果中分别在无 active、有其他组 active 的状态下点击网页跳转，再按 Enter，只激活网页；继续 ArrowDown/ArrowUp 时按实际显示顺序移动。现有组件测试检查了分类数量和 `scrollIntoView` 调用，未证明后续键盘激活目标。

**证据级别**：源码确定的显示位置与键盘选择状态不一致；本轮按约定未运行交互测试。

### 取消和分类席位检查结论

- `api.ts` 用同一个待定 Promise 建立当前 JS 文档的查询会话，quick/page 共用会话但分别使用 lane；模块级请求 ID 持续递增，React 重挂载不会退回旧 ID。初次建会话失败会向调用者报错并允许下一次重新建立。
- App 的 quick/page cleanup 分别发送对应 lane 的取消，并立即使旧 UI 序列失效。page 在 overview 回包后才建立搜索 ID，overview 之前被清理的旧任务会先通过序列检查退出，没有发现清理后再启动查询的确定路径。
- 原生在进入线程池前登记 token，lane 的取消保存最高 ID，能够拦住先取消后到达的命令；旧取消不会取消更高 ID，新 quick 不会取消 page。新 session 重置两 lane，旧 session 的请求和取消均被拒绝，没有发现它们覆盖新会话的确定路径。
- core 在等待状态锁前后检查 token，在独立连接安装 SQLite progress handler，返回前再检查；guard 会卸载 handler。没有发现共享连接导致其他 lane 被误中断的路径。尚未得到锁的取消要等锁返回后才能报错，这不等同已经运行的 SQLite VM 无法取消，也不是本轮新增功能错误。
- 分类席位仅在 `kind=all` 且全局候选超过 30 时启用。每类最多取十条，不足部分由全局顺序补齐；补选的分类型 SQL 仍把授权、工作区条件置于 LIMIT 前。入选后统一按精确/前缀/名称包含/路径包含、名称、UUID 排序，App 再稳定按类别分组，各组内部保留该顺序。
- 全局存在 31 个候选且入选集合最多 30，因此总能找到一条未入选全局候选作为 `has_more` 哨兵。当前实现不会把第 31 条作为重复资料填入前 30，也未发现稀少类别导致余位未填满的确定路径。完整搜索仍独立使用 101 条分页查询，未被快速搜索预留策略改写。
- 除上述分类跳转 P2，本轮未发现确定的晚响应覆盖、双 lane 互相取消、分类配额越权、排序或 `has_more` 新缺陷。该结论是静态复核，不代替根任务的完整测试与性能证据。
