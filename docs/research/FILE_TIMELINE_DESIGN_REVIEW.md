# 文件时间线与日历设计评审

日期：2026-11-19。范围：当前 Rust Catalog、SQLite、Activity 与产品要求。只讨论真实观察证据与用户回顾，不把系统通知数量当作编辑次数。

## 结论

用户需要的是“某天处理了哪些资料”，默认时间线应以文件修改、首次发现和应用内打开为主体。工作区创建/改名等管理事件保留在独立的应用操作筛选里，降低默认信息噪音。左侧月历负责选日与显示有记录的日期，中间按日分组，右侧快速返回最近工作区/文件。页面布局可参考用户图片，但不能照图写出本应用没有观察到的修改历史。

当前可采用现有 `activities` 表演进，而不新增第二套事件系统：增加 `source` 和 `file_modified_at`，`at` 保持事件被本应用可靠观察/执行的时间。文件变化由 Catalog 比较已存状态后写入，同资源变更处于同一事务。时间线查询从 Rust 返回；前端只负责筛选输入、本地日期边界和视图状态。

## 已核对的当前事实

- `catalog.rs` 扫描文件 metadata，提交前复核物理身份，按 identity 合并同一资源。新旧字段为 `modified_at`、`size`、`status`、`location`，当前没有生成文件变化事件。
- `activities` 只有 `id/kind/name/resource_id/at`，当前写入主要是工作区、关联、网页与打开操作。`overview()` 只返回最近 100 条，不能直接拿它计算整月日历。
- 文件资源可属多个授权根，扫描采用代次检查；重复根会再次提交同一资源。事件必须基于提交事务内的状态转移去重，不能按“扫描到一次”写一条。
- 只有完整扫描成功才将未发现记录标 missing。部分失败、取消、离线不得推导删除。
- 全局读取使用 `VISIBLE` 按当前授权与当前路径过滤；工作区保留撤权资源匿名占位。时间线和日历计数都必须使用当前授权过滤。
- PRD 原有动态允许文件最新修改与应用操作，并明确区分 mtime 与观察时间、关闭期间不能重建全部历史。用户本轮已明确增加日历维度并提高文件变化优先级；原 PRD 对复杂日历的排除不能再作为拒绝这项明确授权的理由。

## 事件语义

| kind | source | at | file_modified_at | 用户可见含义 |
|---|---|---|---|---|
| `file_discovered` | `filesystem` | 第一次成功入库时 | 本次读取到的 mtime，可空 | 首次发现/纳入索引；不是文件创建时间 |
| `file_modified` | `filesystem` | 本次成功确认变化时 | 本次读取到的 mtime，可空 | 本应用观察到文件修改信息发生变化 |
| `opened` | `app` | OS 接受打开请求后 | 空 | 通过 WorkTwill 发起打开，不保证编辑器加载完成 |
| `relinked` | `app` | 用户明确修复成功时 | 空 | 用户修复引用，不伪造历史文件变化 |
| `workspace_* / linked / unlinked / transferred` | `app` | 事务提交时 | 空 | 低优先应用管理记录，默认不混入文件回顾 |

“首次存入”容易暗示复制或导入。WorkTwill 不写源文件，推荐显示“首次发现”或“加入资料库”，辅助说明“不移动原文件”。手动拖入已发现文件只是工作区建立关系，不生成第二条 `file_discovered`。

初次索引一个 2024 年最后修改的文件，应记录今天首次发现和文件 mtime 2024 年；不能插入“2024 年本应用观察到修改”。如需让首次使用用户按旧修改日找回资料，可另提供“文件最后修改日”快照视图，明确它不是完整历史事件。用资源表构建快照时需使用独立标签/来源，不与真实 `file_modified` 事件伪装成相同证据。

## 状态转移与去重

1. 在 Catalog `commit_batch` 的当前事务内读取原资源字段。
2. 新 identity 对应新资源：写资源、归属和一条 discovered。
3. 原 identity 已存在且 mtime 或 size 改变：写 modified；变更前后字段同事务更新。重复根/后续重扫读到新状态，自然不再插入。
4. 原 status missing、现在确认同一 identity：恢复 available；建议后续单独 `file_reappeared`，V1 至少不误记为文件新建。若 mtime/size 同时改变可仅保留 modified，避免一轮恢复多条噪音。
5. location/name 改变、身份未变：建议单独 `file_moved` 或 `file_renamed`，不能标为正文修改；如果 V1 不展示该类，仍维护当前资源定位，不编造修改。
6. 同路径不同对象：仍是新的 UUID、新 discovered；旧关系保留且状态待修复。不能因 mtime 接近合并。
7. missing 只在完整扫描成功且不存在其他有效归属时形成一次状态转移，不将每次扫描 missing 再写事件。暂停/撤权不是文件丢失事件。

不要对 `(resource_id,kind,mtime)` 建唯一约束：文件的 mtime 可回退，用户也可能撤销一次修改后再次保存成相同值。正确的去重来自“旧状态→新状态”原子比较。系统通知可能合并、重复或丢失，不宜建立一通知一事件的模型。

仅观察 metadata 意味着相同 size+mtime 的正文改写不可见。应保留这一限制，不为了声称完整追踪而读取全部正文、计算内容 hash 或写 sidecar。

## 观察日与文件修改日

推荐支持明确的时间维度切换：

- **发现时间**（`observed`）：所有事件按 `at`。证据完整可解释，但重启后发现的昨天修改会集中在今天。
- **文件修改时间**（`file_modified`）：`file_modified` 使用可靠、有效的 `file_modified_at`；首次发现和应用事件仍按 `at`。卡片展示“文件最后修改 X；本应用于 Y 观察到”。未知时间不显示 1970。

应用关闭期间即使文件多次保存，重启对比只能产生本次观察到的最新状态一条事件。日期视图不能用最后 mtime 拆成多条历史记录。未来时间戳和异常旧时间不静默修正；可以回退到观察时间并显示文件时间异常或暂只作为详情字段，但需要明确协议。

## 日历、时区与分页

- SQLite 保存 UTC epoch 毫秒。前端使用用户当前本地时区建立某日的 `00:00` 与下一日 `00:00`，传 `[from,to)`，不要以 `+86400000` 推导下一日（夏令时日可能 23/25 小时）。
- 月历以本地月初至下月月初的半开范围查询。后端返回事件 effective timestamp 和 count，前端统一以同一时区归到本地日期。
- 日历计数独立查询全月数据，不受当前时间线 100 条上限影响；必须复用 kind、workspace、basis 和授权过滤。否则会出现日历有红点但点开无权限资料，或 100 条以后日期永远无点。
- 默认月历查询应有边界，避免返回全部历史。可按 UTC 小时桶汇总；若要正确覆盖半小时/45 分钟时区与 DST，后端必须考虑时区边界或直接返回精确 `at,count`。V1 本地历史规模可先用后者，不能把 UTC 日当用户本地日。
- 时间线顺序统一 `effective_at DESC,id DESC`。最小 offset 分页可先实现，但持续新增事件时可能重复/漏项；正式规模优先 keyset 游标 `(effective_at,id)`，携带授权版本/业务 revision。权限版本变化时清空前端旧页和日历。
- 工作区筛选基于当前资源关联即可，界面解释为“当前工作区的资料”；它不证明历史发生时资源就在那个工作区。若需要历史工作区语义，需事件快照字段，不在 V1 默默推断。

## schema 与恢复

- 当前 `event()` 用 `INSERT INTO activities VALUES(...)`，加列时先改为显式列名，否则所有现有事件写入都会失败。
- 旧 schema 迁移新增 `source DEFAULT 'app'`、`file_modified_at NULL`；不从当前资源状态回填历史修改。
- 提升 schema 版本，迁移放在事务内。备份恢复的 staging 也运行同样迁移；不能让主库升级后所有旧版备份都不可恢复。
- 恢复保留真实历史，撤销历史授权，再重建派生查询；恢复本身不向源文件写入，也不将全量恢复记录伪装成今天 discovered。
- 对 `activities(at,id)`、`activities(resource_id,at,id)` 和文件事件时间增加按实际查询验证的索引，先检查查询计划，不能无依据添加所有组合索引。

## 最小验收集

1. 初次扫描 100 个文件：100 条 discovered，文件 mtime 作为辅助，重复扫描事件数不变。
2. 父子重叠根并发扫描：同一 UUID、一次 discovered；mtime 变化一次只有一条 modified。
3. 原位修改、同大小改写且 mtime 改变；mtime 回退；事件正确且源字节由测试动作改变，索引操作本身无写入。
4. 应用退出期间连续修改，重启只观察最新变化，不补造中间次数；保存 fixture 标记验证实际内容。
5. 删除/重现/根离线/部分枚举失败分别检查，不因扫描失败伪造删除，不因复现创建重复资源。
6. 同路径不同物理身份生成新 UUID，旧工作区不继承；时间线可区分首次发现与旧对象不可用。
7. 撤销最后授权后，列表和日历计数均隐藏资源；重叠授权保留时仍可见；匿名占位不泄露名称。
8. 本地月初/月末/跨年、闰日、夏令时与非整点时区的半开范围正确；23:59:59.999 与次日 00:00 不重复。
9. 某日超过 100 条仍显示完整日历 count，分页不混入其他日；所有时间相同的事件按 id 稳定排序。
10. 旧库升级与旧备份恢复后应用事件保留、source 为 app，不补造文件历史。
11. 删除工作区后历史文件事件仍可按有效授权访问；不可进入已删除工作区。
12. UI 空日、加载、错误、无管理位置、首次发现、修改、应用打开和来源图例；中英显示不暴露内部 kind。

## 官方依据

- Rust `Metadata::modified()` 是 metadata 中的最后修改时间，在 Unix 对应 stat mtime，Windows 对应 ftLastWriteTime；可能不受平台支持，不能假定恒存在：<https://doc.rust-lang.org/std/fs/struct.Metadata.html#method.modified>
- Apple FSEvents 可能合并事件；`MustScanSubDirs` 需要递归重扫，Kernel/UserDropped 需要重新核对受监视范围。这支持“通知是触发核对的线索”而不是“完整编辑审计”：<https://developer.apple.com/library/archive/documentation/Darwin/Conceptual/FSEvents_ProgGuide/UsingtheFSEventsFramework/UsingtheFSEventsFramework.html>
- SQLite 官方说明 offset 与偏移量成正比，滚动窗口可用 row-value 比较进行 keyset 分页：<https://www.sqlite.org/rowvalue.html#scrolling_window_queries>

以上为官方接口语义与当前源码评审，不是已完成的原生产品验收。
