# 0036：在原生边界统一外部拖入坐标

日期：2026-11-20。状态：实现及自动回归通过；修后 Finder 真实目标矩阵尚未通过。

## 实际问题与证据

用户反馈 Finder 外拖似乎只能加入首项工作区。没有继续把它概括为跨窗自动手势问题：本轮在旧行为上临时增加本地探针，捕获了真实原生 `files-drop-started` 与 `import_drop`。

屏幕倍率和 `devicePixelRatio` 均为 2，原生坐标 `(421,526)` 落在工作区 `b26967ab-8ebb-428e-be67-36c5dc48e8d9` 的可见卡片内。前端除以 2 后用 `(210.5,263)` 命中 DOM，没有工作区，于是以 `null` 目标导入；可见回执为 0 新增、1 已存在。探针是在两次观察间捕获事件，不推定由用户手动还是之前的工具尝试触发。

核对锁定依赖：Wry 0.57.3 的 `wkwebview/drag_drop.rs` 直接使用 AppKit `draggingLocation` 与 view 高度，单位为逻辑点；tauri-runtime-wry 2.12.5 直接包装为 `PhysicalPosition`，没有乘屏幕倍率。Windows 路径使用 `ScreenToClient` 的物理像素。缓存 crate 与已安装源码一致，没有修改依赖或本机 registry。

这确认了原生至 DOM 的坐标单位错误。它会导致其他卡片偏向左上方目标或未命中后使用当前工作区；代码没有硬编码首项或某个 UUID。用户所述具体首项现象、换序后的原生表现仍需修后真实复验，不用源码和模拟测试代替。

## 最小修复

- 在 `src-tauri/src/drop_coordinates.rs` 将 macOS 逻辑点乘以事件当时的窗口屏幕倍率，统一成既有事件契约中的物理像素；其他平台原值保留。
- Enter、Over、松手开始及身份捕获完成使用同一坐标单位。取得屏幕倍率失败明确发出错误，不静默猜测。
- React 继续按 `devicePixelRatio` 转 CSS 坐标；hover 与松手命中、UUID 优先及未命中使用当前工作区的既有行为不变。目标仍在松手时固定，慢身份捕获或后续导航不改目标。
- 不改资源 UUID、Rust token、授权边界、文件导入与去重事务、内部拖拽或任何领域模型。
