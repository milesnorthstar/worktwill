# 0015：时间线成本分段与反向关联索引

日期：2026-11-20。状态：迭代017实施；整月日历及深分页性能仍未解决。

014的多资源时间线结果明显慢于单文件重复事件。不能根据总时延直接归因为分页，因此将事件SQL与日历SQL生成提取为私有函数，正式API与cfg(test)分段验收器共用。测试诊断仍在同一读事务里执行原始事件读取、资源DTO组装、整月日历和版本读取；计划采集放在计时之后。不添加产品遥测或对外IPC。

100k实体/100007事件，offset0/100/10000/97500每个4样本（包括首样本，不称稳定P95），16次独立原始Vec oracle核对正文/关系/排序/日历/版本全部一致。Rust bundled SQLite3.50.2实际计划确认：整月日历已经按每天时间范围SEARCH，但每次仍对约100k事件重复做授权及资源关联，首页约290ms主要花在日历；末页事件读另约290ms。offset0的事件读取仅约0.5ms、资源DTO约6.5ms。日历内部30行排序不代表对全月100k活动排序。

资源DTO逐项按resource_id读取工作区关系，原计划为SCAN复合主键(workspace_id,resource_id)。新增非唯一覆盖索引workspace_resource_memberships(resource_id,workspace_id)，不改变关系唯一性或业务状态；迁移入口对已有v3库补建。真实旧库回归删除索引后重开，确认由SCAN改为SEARCH覆盖索引，20个关联完整、DTO不变、权限/revision不变、integrity_check=ok。名称搜索、时间线、普通资源及删除/合并消费者沿用已有resource_db和关系表，不另建数据源。

有from/to的时间线列表改为直接>=/<范围条件；无边界仍显式绑定NULL，并保持半开区间。专用回归覆盖观察/文件修改两种时间，单侧与双侧边界、两端事件及实际范围SEARCH计划。只证明选日计划与语义；本轮分段样本使用整月无列表边界，没有给选日计时性能结论。

优化后相同16项oracle零错，首页资源DTO由约6.5ms降至1.6ms，反向计划为SEARCH覆盖索引；整月日历仍约283–298ms，末页总耗时约564–581ms。没有把小幅关联优化称为整体性能通过。原始before/after诊断JSON及日志保留，非正式Store::timeline总体SLA、原生可见延迟或冷盘证据。

后续可评估有界的版本一致日历复用与时间线末项游标。日历复用键必须覆盖Store/session、权限/revision、日界、basis/filter/workspace；第一页成本仍需另解，不能用热缓存掩盖。时间线目前仍offset，未修改DTO/前端分页协议。
