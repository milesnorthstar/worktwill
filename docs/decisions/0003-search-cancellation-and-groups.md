# 0003：请求独立的 SQLite 取消与混合搜索席位

日期：2026-11-20。状态：已实施，原生窗口及性能证据另记于验收报告。

## 问题与行为

F03/F14 原要求包含后端查询取消和混合资源呈现。此前前端序号只防止旧响应覆盖，SQL仍继续执行；全局Top30可能全是文件，匹配的网页/工作区没有机会进入下拉。

本轮保留Rust授权与持久数据归属，只补搜索执行和展示：

- Core `SearchCancellation` 每请求独立，SQLite连接也独立。开始前、取得读锁后、组装结果和返回前检查取消；运行中每1000 VM指令的progress_handler可实际停止SQL。RAII清除handler。取消返回`search_cancelled`，不返回伪装成功的空数组。既有`Store::search/search_page`保留默认未取消token的入口供CLI和基准调用。
- 原生仅两个固定lane：quick/page。新请求取消同lane旧请求；取消先于请求到达时留下最高ID水位，迟到请求不能重新运行。旧请求取消不影响较新ID，也不影响另一lane。不保存持续增长的请求map。
- `begin_search_session`由Rust生成查询会话UUID；新WebView上下文取消两lane并重置水位，旧会话不能反向抢占。它是查询取消上下文，不是账户、授权或数据库session。前端API模块懒初始化一次，request ID在模块内递增，组件重新挂载不归零；WebView重载重新建立原生会话。初始化失败向调用者报错，下一次明确搜索可重试；取消不会自行新建会话。
- App effect清理时分别取消quick/page，同时保留前端响应代次校验。40ms去抖尚未发出的请求直接清timer；已经发出的请求调用原生取消。查询session/request_id与已有page.session/permission_version/revision分别承担执行隔离和数据授权校验，不能混为一组。
- 对all且授权匹配>30的快速搜索，每类workspace/file/web预留至多10项，稀少类别的空位按全局相关性补足。每类候选仍先执行授权、类型和工作区过滤；入选后按原相关性/规范化名称/ID排序。显式类型、≤30匹配及完整搜索页保持纯全局排序。第31项只判has_more，不能返回重复资料。
- 增加可重建的`search_documents(kind,name,entity_id)`索引支持类型候选，不改变业务schema版本3。完整搜索展示所有匹配；分类预留只改变快速下拉的选集，不减少完整结果。
- 搜索面板列出各类计数并可跳转。跳转同步到该类首项的键盘索引，保留搜索焦点后Enter不会打开滚出视口的旧结果。

## 代价与证据

混合下拉预留类型席位后，不承诺其选集等于不分类型的全局Top30；同一类型内部顺序和完整搜索仍保留原排序。空缺类别查询借助复合索引避免扫描大量文件；新增查询和progress callback的开销必须重测，不能沿用旧性能数字宣称通过。

Core测试等SQLite真正开始执行后才取消，确认原始OperationInterrupted、正式Store两个查询入口均触发中断，随后连接和查询可用。原生session/lane测试覆盖重载、重复/旧ID、取消先到；API/组件测试覆盖模块会话、取消清理和分类键盘行为。它们不等于真实Tauri IPC/原生输入可见延迟验收。

100k混合文件/网页/工作区使用独立全量内存oracle与正式磁盘Store测量，保留原10000–500000规模基准，见 [验收与迭代记录](../ACCEPTANCE.md)。
