# 0006：扫描复用搜索投影，提交当前元数据

日期：2026-11-20。状态：迭代007已实施；大目录原生体验、空闲资源和Windows仍须验收。

实际10k合成文件的正式release扫描基线显示：首次扫描5.636秒；不变重扫并发搜索时8.900秒，搜索P95 91.491ms，数据库从29,347,840增至35,098,624字节。文件创建不计入扫描耗时。原因包括每个文件都删除重建两套FTS，以及同路径旧资源查询缺少索引。

`search::project`在自身比较规范化后的kind/name/location，并确认两套FTS对应行存在。内容不变时不更新投影；投影或FTS行缺失仍走原写入路径。mtime-only仍更新资源和观察事件，日期与排序仍查资源表；没有在Catalog按mtime相同就提前跳过。显式重建先清映射，仍强制重建全部投影。FTS行存在但内容错误需显式重建；不宣称正常重扫能修复任意FTS损坏。

新增派生、非唯一`resources(location)`索引，覆盖Catalog和独立文件导入的同路径查询，保留同路径旧UUID占位。旧v3和恢复暂存库打开时幂等创建，不改领域schema版本。已有大库首次建索引成本须另测。

额外回归证实重叠根旧批次会将已更新的size从43写回11，并可能多记一次修改。提交时现复读当前文件metadata、复核物理身份，要求当前canonical path仍等于捕获路径，以当前mtime/size与数据库比较。代次、授权、UUID和file_roots更新保持原归属。复验失败向扫描循环回传并累计failures，收尾不将其当成无失败完整枚举。

新增测试覆盖投影不变时零SQL变更、两套FTS分别缺行、改名旧词消失、错误内容显式重建、重叠批次不回写旧metadata/不多记事件、消失候选和Unix父目录换链接不发布。后两项直接验证提交边界，未通过原生全流程实证扫描收尾；stat/identity/canonicalize不是原子句柄操作，检查后的文件变动窗口仍存在，打开前复验继续保留。

这不是文件系统差量枚举实现。监听仍合并为授权范围完整元数据重扫，普通资源写入和根代次仍更新；不把FTS复用写成只访问发生变化的文件。实测结果与所有前后日志见[验收记录](../ACCEPTANCE.md)，原生渲染、100k真实文件、洪峰、空闲CPU/RSS、云盘及Windows不能由本次10k样本推定通过。
