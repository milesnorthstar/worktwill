# 0026：最近使用与原生打开绑定实际对象

日期：2026-11-20。状态：迭代026实施，执行结果见验收记录。不改schema7、前端DTO或原件。

对照F04/F08复核历史来源的消费者时，发现时间线的授权修复尚未覆盖最近使用：跨物理identity重新指向或合并后，旧opened仍挂在canonical UUID上。原查询仅按UUID选择、按所有opened的最大时间排序，会让从未打开的B继承A的使用记录，或让B借A的新时间排在C前。三项真实文件回归在修复前均失败，日志保留。

最近使用的选择和MAX(at)共用同一个条件：文件opened必须存在与当前文件identity相同的观察来源；网页不具有文件origin，保留其原有opened语义。同identity改名、同卷移动继续保留使用记录；跨identity修复后的B需有B本身的打开记录。具名旧A活动仍可在动态中按原观察来源权限显示，不能据此将B当作曾被打开。缺失来源或identity不猜测继承，不把旧记录改写为新对象。

原生打开原先分为按UUID解析、调用系统、再按UUID记录。在阶段间重新指向、合并或恢复时，最后一步可能把A的打开写成B。增加仅Rust持有的ResolvedOpen：字段私有、不Clone、不序列化、不作为IPC/DTO。prepare_open沿原定位恢复入口执行，随后在同一读取事务重新核授权、物理身份、canonical位置与文件类型，保存观察名称、identity/URL、权限版本、Store session及恢复epoch。定位恢复本身仍可能更新应用映射，不能宣称整个prepare没有应用数据库写入。

原生宿主只用快照的位置和类型调用系统。系统接受后，record_open_checked按值消费快照，以短写事务复验对象、位置、实际metadata、当前权限、session和恢复epoch，再保存快照观察名及来源。不使用完整revision，因此无关扫描、收藏、工作区变更或其他打开不会使同对象请求失效；不跨系统打开长持锁。现有Core便捷record_open用于Core调用及既有测试，正式宿主只使用checked路径。

变化时明确反馈“系统已接受打开请求，但资料或授权已变化，本次活动未记录”。数据库/锁错误保留真实错误码，并说明已接受、未记账，避免把记账失败伪装成系统未接受打开。代价是额外短事务与metadata复验，以及权限变化或同身份换路径恰逢打开时保守拒记一次活动。系统按路径打开本身仍有检查后的时间窗口；系统接受也不证明宿主已完成加载。

同轮复核还发现文件选择器返回的整批路径未走checked导入，而拖入已有这项能力。私有PickedFiles在返回路径后立即复用capture_import_selections固定整批身份，再复用import_files_checked逐项导入；不新增授权API、兜底或第二份导入逻辑。批次捕获后被替换的后项失败，前后其他项继续成功，替换对象不获授权。取消仍在原生None分支提前返回，丢弃已捕获批次也不提交授权。选择器返回到首次捕获的窗口、真实OS选择器和打开行为仍须原生验收，不由纯Rust测试替代。

新增检查包括真实relink/merge/排序、网页无origin、选择批次替换/取消、正常打开来源、无关revision、撤权/重授、恢复、同identity换路径、未被扫描观察的物理替换、URL/title变化及跨Store快照。与侧栏第13项以后拖入、读取中范围状态的UI回归分别执行，既有测试和失败证据保留。搜索和时间线SQL未因本决定再次变化，规模数据保留本轮已测的两次完整链，不把这些新边界测试算作原生U8通过。
