# Windows 保存连续性 PoC：多 agent 对抗审查

日期：2026-11-21。用户明确要求多 agent 审查；分别从事件证据、身份/权限反例、当前实现接入三个方向只读审查。本记录确认实验方向，不批准正式身份策略变更，不表示 U8 已修复。

## 结论

同意先做“小型独立 PoC”，方向是稳定 Resource UUID、多重定位证据及保存事件关联。不同意现在就把同路径替换判为同一资源，也不把创建 Object ID 作为已经确定的修复。

Resource UUID 已经是现有业务主键，无须重构收藏和工作区主键。真正缺口是更新物理绑定时的文档连续性证据，以及该证据能否支持单文件授权延续。

用户提供的 Tabbles 历史修复描述可以作为调研线索。本轮未独立核验其原始页面，且即便描述属实，也不能据此推断其算法、最新 WPS 兼容性或误关联风险。

## 三方一致发现与对抗结论

1. Windows 当前 notify 底层使用 ReadDirectoryChangesW；应用在 main.rs 回调中只传路径到 KnownChanges，丢弃事件类型等信息。KnownChanges 去重、容量256、溢出淘汰旧路径。它适合触发复核，不是完整证据日志。
2. 当前 ingest/catalog 按物理 identity 匹配资源；身份改变会产生新资源并让旧对象待确认。因此不能只改一处“相同路径复用 UUID”，否则扫描和单文件维护会出现不一致。
3. 完整 rename 链、时间接近、同路径、相同创建时间可以支持候选关联，但不能单独证明用户意图。任意程序都可以制造“临时文件创建→旧文件改名→临时文件改成原名”的相同序列。USN Journal 提供操作历史，不提供可信的“这是编辑器安全保存”判定。
4. 单文件授权是独立阻塞：当前 relink_impl 在物理身份变化时撤销旧 file grant。复用 UUID 不得绕过这一规则，向新对象静默授予访问，也不得使旧身份历史名称重新可见。
5. Object ID 可作为额外测量；其是否保留依赖实际保存流程。不能保证 WPS 使用 ReplaceFile，也不能将 Object ID 与 File ID 混用。

## 第一阶段：旁路观测，不更新正式资源绑定

在已确认测试根内部新建独占目录，记录原始事件、序号、单调/UTC时间、路径、可取得的事件配对信息、File ID、卷、创建时间、已有 Object ID，以及观察错误、缺口和溢出。采样时对象可能已经消失，必须记录读取失败，不能补猜瞬间身份。

使用独立日志与独立测试库，不写生产 SQLite。现有 office_acceptance 可复用关系核对结构，但不能调用人工 relink 后登记自动恢复通过。先采集原始信息，再离线评估规则，防止边采边换绑影响对照事实。

实验至少覆盖：

| 正例/控制组 | 反例/故障组 |
|---|---|
| 本机 WPS 连续保存、关闭文档再打开保存 | 保存期间保留旧对象为 .tmp/.bak，确认引用不跟到旧对象 |
| WorkTwill退出期间保存，重启复核 | 同路径删除重建、普通文件覆盖、刻意复现相同 rename 链 |
| Explorer改名、同卷跨目录移动 | 复制和另存副本，同内容双文件与相似内部文档属性 |
| 两工作区、收藏、最近使用保持 | 撤权、暂停、仅单文件授权、授权目录外目标、监听丢失/溢出 |

创建 Object ID 必须作为单独实验组，与无标记控制组比较；仅操作合成文件，记录写入前后和每次保存后的 ID。当前架构禁止默认创建该元数据，本次方案审查不自动视为执行授权；正式接入更需独立批准。先执行不写元数据的观测并不依赖这一批准。

## 第二阶段：证据规则与实现门槛

只在第一阶段得到实际区分能力后设计 ContinuityProof。至少绑定旧资源UUID/旧identity、候选新identity、当前卷和规范路径、证据来源与有效区间、监听/日志代次、权限及业务修订快照。不得把“事件序列看起来像保存”命名为确定证明。

在 Rust gate/事务边界重新核对当前授权、目录/候选对象身份、修订及证据是否仍适用，再原子更新绑定、投影和当前元数据。保存延续不能伪造手动重新指向记录，也不能把历史活动来源全部改成新对象；恢复屏障与并行扫描必须覆盖该提交。若新对象已入库并已有独立业务关系，不能静默合并。

以下情况拒绝自动延续：观察缺口、Journal失效/回卷或卷变化、存在多候选、身份复核竞争失败、授权改变、反例与正例不可区分、可能把引用指向备份/临时旧对象。保留原关联并进入待确认；不能承诺离线增量扫描必能重建保存语义。

USN先列为可选的离线证据实验，必须记录普通用户权限和可用性；不先把管理员权限、全卷扫描或完整USN基础设施引入V1。

## 通过与停止标准

- 五类用户清单逐项记录实测结果，额外列正反例、UUID/资源数量、收藏、双区、最近使用及权限/历史状态。当前均未因本方案审查而新增通过。
- 任何错误继承到副本、备份、同名替代物或权限外对象，均判失败；有限样本零错误不证明对所有编辑器安全。
- 若普通替换能产生同样的全部判据，则该规则不能在现有严格语义下自动接入。需更强原生证据，或产品负责人明确选择新的“路径槽位/授权范围”语义并修改PRD与架构；后者不是本轮默认方案。
- Object ID保留失败只否定该实验路径，不否定整个PoC方向；不得改用路径猜测补成通过。

最终建议：批准独立观测 PoC 方向；正式自动换绑暂不进入实现。先用真实 WPS 轨迹与可观测等价反例检验最小规则，再决定是否值得增加 USN 或受控元数据策略。
