# Windows 文档连续性：验证结论与长期方案

2026-11-21。依据两轮独立实验，不是已经接入正式候选的功能说明。

## 用户确认后的实施约束（优先于下文早期建议）

用户已明确批准四层方向、系统明确替换的逻辑版本延续及显式同意后按需建立Object ID，正式产品规则同步至PRD §4.3与ARCHITECTURE Windows章节。无需再索要同一产品取舍确认。

持久锚点、卷/目录身份、当前对象、版本、唯一性及冲突检查满足时，缺少在线事件不单独否决退出期间恢复。旧单文件授权必须在物理身份变化时失效，包括先单文件授权、后目录授权的混合情况；最近使用解析、历史展示授权、当前访问授权独立判断，不能只放宽身份条件。

本轮追加真实WPS COM连续12次保存与300次后台扫描：捕获锁文件及多份不同identity的contract.docx记录，最终14个文件资源，实验判定reject_existing_resource。未捕获替换源在.tmp名称下提前入库，因此该特定时序仍未完成强制验证；不据此允许静默合并或“没有收藏就合并”。原始race.jsonl已归档。这个结果证明当前没有连续性处理的扫描会积累保存版本记录，不是新架构统一入口已经失效的证明。

混合授权负向实验已复现：先import_files单文件授权，再grant_root，WPS保存后沿用早期SQL实验绑定，再撤目录；file_grants仍active=1，收藏与resolve仍可用。该负例只存在隔离PoC，不能作为正式安全实现；确认续接事务撤销旧grant是必须实现的要求。见mixed-grant-naive-{apply,revoke,state}.json。禁止把这个负例改名为撤权通过。

同意目录追踪与逐文件锚点建立结果独立保存/展示；关闭追踪或撤权停止后续操作，不自动删除或重置已有Object ID。迁移、备份恢复与多次保存重启必须纳入验收。当前example仍仅实验，正式服务、schema、UI同意及自动接入尚待实施。

## 最终技术结论

推荐独立的文档连续性层，保留现有物理identity语义及Resource UUID。NTFS Object ID作为可选择启用的文档追踪锚点，事件作为候选定位和失效信号，不作为单独的文档身份证明。不能采用只改platform::identity或同路径复用UUID的补丁。

本机WPS实验连续保存保留Object ID，复制及另存副本不继承。因此它是有用的Windows锚点。但File.Replace覆盖无关文档也保留目标Object ID；本轮实验库再次证明按标记策略会把原UUID与关系交给被覆盖后的内容。这是该策略的明确语义边界，不是已经解决的误关联问题。用户已接受明确替换的版本延续语义；仍须逐项复核锚点、卷、目录授权、绑定版本与资源冲突，不能仅凭该标记默认上线。

## 第二轮应用层实测

新增隔离example `continuity_poc`，只允许已确认临时根下的夹具。使用真正Store建库、授权、扫描、双区、收藏，调用打开记账接口建立recent基线（未向系统发出打开，不算真实打开验收）。关闭Store后，实验SQL仅模拟候选绑定更新，再重新打开Store执行扫描与查询。不是生产自动恢复实现，也没有以manual relink冒充自动恢复。

| 项目 | 观察 |
|---|---|
| WPS Save后按标记实验更新 | 同UUID、双区2、收藏保留、可resolve、文件资源数1 |
| 最近使用 | **丢失**：当前查询要求opened活动原identity等于现identity；只更新资源绑定不足以满足完整需求 |
| 复制 | 扫描后资源数2；原UUID仍双区，副本没有继承原关系 |
| 无关DOCX经File.Replace覆盖 | 标记规则同样接受，原关系跟随目标覆盖内容，说明误继承边界真实存在 |
| 撤销目录授权 | 决策reject_revoked，收藏/最近入口空，resolve返回not_authorized，双区关系保留 |
| 关闭并重开实验Store | 撤权结果保持；不是原生候选应用重启端到端验收 |

证据：`docs/validation/2026-11-21-windows-binding-poc-{save,copy,unrelated-replace,revoked,reopen-revoked}.json`。example构建、fmt及严格clippy通过。未做正式schema迁移，未验证单文件授权续接、并发CAS、崩溃恢复或原生候选U8；不得登记全面支持。

## 维护与扩展设计

### 1. 保持三个概念独立

- `Resource UUID`：逻辑资料及收藏/工作区关系，不因定位变动重建。
- `PhysicalIdentity`：当前对象事实，继续用于打开前复验、TOCTOU保护、复制判别；不改现有字符串解释，不把Object ID混入唯一物理身份。
- `DocumentAnchor`：卷内Object ID等可选锚点，记录provider和策略版本；不是跨卷或跨平台通用标识。macOS以后可独立验证Document Identifier，不能沿用Windows结论。

### 2. 单独的证据与决策服务

Rust私有适配器采集物理身份、锚点、定位信息、事件完整性；核心返回SameObject、ContinuationCandidate、Ambiguous、Conflict、Unavailable。读取已有锚点与创建锚点是两个接口，后者必须显式启用、复核授权、记录结果；查询和扫描不能悄悄创建。

有界事件采集独立于现有KnownChanges触发队列，保留来源/代次/缺口。锚点不支持、卷变化或冲突时不能降级成路径猜测；事件缺口不单独否决持久锚点核对。USN可后续实现为可选locator/reconciler provider，不要求管理员、后台服务或创建Journal作为首版前置。

### 3. 独立事务提交入口

新增私有ContinuityProof，携带旧UUID、旧物理identity/绑定版本、新对象快照、锚点及策略、授权版本、restore/scan epoch与证据引用。提交必须在gate/短事务内CAS，再次复验身份/授权，保持现有锁顺序，并使在途打开与旧游标失效。

扫描批次、原生通知刷新、导入及重启核对共用同一解析与提交服务，避免一条入口延续、另一条先创建重复UUID。目标已存在独立资源/收藏/授权时产生冲突，不静默合并；失败保持旧关系，不留下半更新。

### 4. 显式连续性历史

建议分离 `document_anchors`、`resource_binding_history`、`document_tracking_policies`。绑定历史包含前后物理身份、卷/锚点、证据类型、策略版本、观察/提交时间与修订；命名、列与迁移需在实现时确定。历史活动保留原observed identity，不能UPDATE旧activity_origins来让recent重新出现。

最近使用通过已接受且仍符合授权规则的连续性链关联当前文档；历史名称仍按当时观察对象或有效历史范围控制。绑定链不是新的授权来源，不能借它重新暴露已撤权历史。新增索引、恢复/备份及旧库迁移需一并设计，旧数据没有锚点就明确待启用，不追溯猜测。

### 5. 授权与策略独立

目录授权允许读取候选对象，不决定业务身份。仅单文件授权默认仍绑定原物理对象；若产品启用“授权跟随受追踪逻辑文档”，需独立policy与撤销语义，不能因为UUID相同而自动获得权限。暂停、排除、reparse、根替换、权限/恢复代次变化继续适用。

用户已选择“Object ID延续包括ReplaceFile覆盖也视为原文档”，该明确替换延续策略已写入PRD/架构；它不是算法已经区分了用户意图。未启用时保守待确认。不能通过增加若干弱特征得分悄悄改变此语义。

## 实施建议与交付门槛

推荐在该分层基础上实施受控实验版本，先目录授权、单卷NTFS、显式追踪；再完成lineage、单文件授权与恢复。不要在正式版本先上“仅Object ID相同即换绑”，之后再补历史权限。

生产接入前必须同时关闭：最近使用丢失、已确认替换语义的实现、单文件授权、复制/另存、旧对象临时名竞争、扫描并发、撤权/排除、恢复/崩溃、真实GUI连续保存与应用退出/重启取回。技术结构已有明确方案，但这些实现与验收还未完成，Windows V1 U8仍不通过。
