# WorkTwill V1 三 Agent 对抗审查汇总

> 审查日期：2026-11-21  
> 审查对象：[WorkTwill_V1_产品审查与整改方案.md](./WorkTwill_V1_产品审查与整改方案.md)  
> 审查方式：3 个独立 Agent 分别审查产品方向、实现事实与可行性、完整用户闭环与验收；主会话核对主要证据并汇总。  
> 证据边界：完整阅读原审核报告，结合截图、当前 PRD、架构及相关正式源码进行只读审查。未启动服务、运行测试或执行原生验收。源码已有测试不等于本次已执行通过；本文指出的方案风险不等于已确认的运行时故障。

## 一、总体结论

**大方向正确，但原报告尚不适合直接作为研发施工单或交付验收基线。**

报告准确抓住了系统文件噪声、页面职责表达重复、搜索结果难以判断等问题；但将部分设计假设写成了确定结论，并遗漏删除页面后的完整能力承接路径。

三方结论基本一致：

- 认可去噪、明确页面职责、提高搜索可判断性的方向。
- 不认可未经任务承接验证就以搜索排他替代浏览。
- 导航与首页的调整属于可讨论的新产品取舍，不应追认为既有实现 Bug。
- 需要复用已有搜索、事件、权限和身份能力，不能因为截图未充分呈现就重新建设。
- 当前 P0 清单及退出条件需调整，不能以“页面更少”替代“核心任务更完整”。

> **需要减少的是重复决策和无效信息，而不是单纯减少页面数量。**

## 二、值得采纳的方向

| 方向 | 综合判断 | 边界 |
|---|---|---|
| 治理 `.DS_Store` 等系统工件噪声 | 优先处理，截图与源码均支持真实缺口 | 不一刀切过滤所有隐藏文件，不改变授权与源文件 |
| 收藏页去掉通用四 Tab | 认可，确有层级表达冗余 | 截图中收藏已自动选中，并不能证明用户需要再点击一次 |
| 首页让真实工作资料更快可见 | 认可 | 不立即锁死 5–8 条、固定版式或混排算法 |
| 搜索显示命中依据、类型与可辨认位置 | 优先处理 | 保留现有分组、筛选、排序与完整路径悬停能力 |
| 时间线服务于工作回顾，而非磁盘日志 | 认可 | 保留既有事件语义，先去噪与诊断，再判断聚合需求 |
| 不改变源文件、不强制先建工作区、不引入 AI 等范围 | 保持 | 不以本次整改扩张数据源或内容读取能力 |

## 三、实施前应修正或补充的事项

### 1. 不能由“搜索也能找到文件”直接推出“取消浏览入口”

**原报告位置**：第 0.1、0.2、2 节图 04、第 5 节第一阶段。

搜索适合用户掌握部分线索后定向查找；浏览还承担“不知道叫什么，看到了才能认出来”的任务。最近、收藏、工作区无法覆盖从未打开、很久没改、也未整理的资料。

当前完整搜索要求非空关键词，不能直接只选日期、位置就开始查询；现有类型筛选主要是文件、网页、工作区，不等于 PDF、DOCX 等文件格式筛选。原报告先删除页面、后完善承接筛选，存在能力断档。

**建议**：

- 可以讨论取消一级入口，但不要先取消浏览任务。
- 若决定删除，应同批交付可发现的“按位置／时间／类型找资料”路径。
- 明确无关键词条件查询、分页、多选收纳、返回上下文的行为。
- 无须为了补齐承接另建平行“资源库”；优先扩展现有检索路径。

**验收补充**：零工作区、空关键词、不在首页最近项中的旧文件，用户仍能按已支持的条件找到、打开、加入工作区，返回后保留条件。

**证据**：`PRD.md:27,93–108`；`crates/worktwill-core/src/search.rs:288–297`；`desktop/src/workbench/components.tsx:35–39`。

### 2. 明确哪些属于新产品取舍，而不是缺陷修复

当前 PRD 明确保留“所有文件”导航、首页前三张真实工作区卡片及相关资料交互。这不表示旧决定永远不能改变，但原审核报告不能单独证明用户已经批准改变。

**建议**：新增“待确认的基线变更”表，分别列出导航、首页职责、工作区快捷列表等变更及理由。批准后再同步 PRD、架构和验收预期，避免两套相反要求并存。

若用户另有明确批准删除入口的上下文，应据此更新决策状态；但仍需解决上一节的任务承接问题。

**证据**：`PRD.md:14,93,100–107`；`desktop/src/App.tsx:303–306,327,335`。

### 3. 首页“继续工作”需补冷启动、排序与状态规则

首次使用没有应用内打开记录；最近修改可能被批量下载、历史导入和系统文件占据；返回工作区本身也是继续工作。

**建议**：

- 明确无打开记录时的展示策略。
- 明确最近打开与最近修改是分区还是混排，同一资料如何去重。
- 保留工作区返回入口，不把继续工作缩减为单文件打开。
- 先做可逆的排序与密度调整，再用用户任务验证具体条数和版式。
- 首页需保留读取中、读取失败、未授权、授权取消／拒绝、扫描中无首批结果、空目录、已有资料但无打开记录等区别。
- “5 秒获得价值”需限定适用状态；首次可搜索耗时与已建索引后的返回体验分开记录。

现有打开记录证明的是系统接受了 WorkTwill 发起的打开请求并完成相关复验，不证明宿主已完成加载，也不是全操作系统的使用历史。

**证据**：`PRD.md:100–103,220`；`src-tauri/src/main.rs:313–340`；`crates/worktwill-core/src/open_target.rs:87–149`；`desktop/src/workbench/components.tsx:113–119`。

### 4. 时间线已有事件语义，应避免重复建设

当前正式实现已经区分文件修改、首次发现、应用内打开，展示文件时间与观察时间，并说明首次发现不代表文件创建。无变化重扫不新增修改事件也有对应逻辑和测试。

**建议顺序**：

1. 查清截图中 81,168 条记录的事件类型、独立资源、系统工件与历史数据分布。
2. 先过滤系统工件。
3. 区分重复记账和真实高频修改产生的展示噪声。
4. 再判断是否需要短窗口聚合。

若实施聚合，需先明确使用哪种时间、是否跨日、日历显示事件数还是摘要数、跨页如何保持稳定。不能只对当前已加载页合并卡片，也不能跨重新指向前后的不同历史物理对象聚合。权限过滤应先于聚合，不修改或丢弃原始事件来获得视觉整洁。

**证据**：`desktop/src/timeline/ActivityTimeline.tsx:182–229`；`crates/worktwill-core/src/catalog.rs:414–424`；`crates/worktwill-core/src/ingest.rs:427–437`；`crates/worktwill-core/src/timeline.rs:125–162,237–393`；`crates/worktwill-core/tests/workflows.rs:717–760`。

### 5. 去噪应覆盖旧数据，并与授权严格分离

当前自动扫描已有少量目录跳过规则，但未处理报告指出的 `.DS_Store`、`Thumbs.db`、Office 锁文件等工件。

> **授权决定能否读取；去噪决定默认是否展示。**

**建议**：

- 不只修改扫描入口，还需覆盖旧库已有工件。
- 默认去噪在查询分页限制前生效，覆盖列表、搜索、动态明细与日历计数。
- 不将默认隐藏伪装成未授权，不破坏工作区引用与打开规则。
- 高级显示不能恢复已撤销权限。
- 用户显式选择、收藏或加入工作区的工件是否豁免，需明确产品规则。
- 不删除源文件，不因去噪随意清除关系或历史。

**证据**：`crates/worktwill-core/src/catalog.rs:39–66,147–174`；`crates/worktwill-core/src/store.rs:111–120,282–310`；`crates/worktwill-core/src/search.rs:230–254`。

### 6. 搜索主要补命中解释，而不是重建已有搜索能力

当前已具备名称／路径或 URL 检索、精确名称至仅路径的排序、工作区／文件／网页分组、完整结果分页与多种筛选、路径悬停。

真正缺口是：返回契约和结果 UI 没有明确给出实际命中依据。数字文件名因父路径包含关键词而命中可能完全正确；没有对应库与请求结果，不能断定截图中的具体命中原因。

**建议**：

- 既有分组、筛选、排序列为保留并验收，不重复开发。
- 命中依据需与后端实际匹配一致。
- 高亮需处理大小写与 Unicode 规范化，不能简单在原始文本找不到词时猜测字段。
- 如涉及 DTO 扩展，遵循 Rust `model.rs` 为事实源并生成 TS 的既有约定。

**证据**：`crates/worktwill-core/src/search.rs:203–254`；`crates/worktwill-core/src/model.rs:87–98`；`desktop/src/workbench/components.tsx:13–15,29–50`；`desktop/src/App.tsx:333–334`。

### 7. “失效状态一致”应改为状态语义一致

| 情况 | 应有行为 |
|---|---|
| 仍授权，但暂时找不到文件 | 可保留已有名称与关系，说明状态并提供修复 |
| 同一路径被另一物理文件替换 | 身份待确认，不自动继承旧关系 |
| 最后一份授权撤销 | 搜索、收藏、动态隐藏名称路径；工作区仅留匿名占位 |
| 仍有其他有效目录或单文件授权 | 按有效授权继续可用，不一概隐藏 |

“一致”不是所有页面都展示同样的“文件名＋打不开”。诊断入口和高级过滤也不能绕过授权；撤权不等于擦除数据库和既有备份。

**验收补充**：在结果显示期间撤销最后一份授权，迟到响应不能恢复旧名称路径；动态计数与收藏同步遵循可见性规则；重叠授权情形单独核对。

**证据**：`PRD.md:227–237,289–294`；`crates/worktwill-core/src/store.rs:265–296,1044–1086`；`crates/worktwill-core/src/catalog.rs:252,403`。

### 8. 将新增能力与界面整理拆开

以下并非简单调整 UI：最近访问工作区、固定工作区、收藏时间、列表／卡片双布局、正文索引与内嵌预览。

当前没有完整的相关访问／收藏时间字段；已有工作区手动排序不能冒充最近访问。正文索引与内嵌 Office/PDF／网页预览属于现行 PRD 明确排除的 V1 范围。

**建议**：本轮先用类型、路径、修改时间、系统定位和默认应用打开改善判断。新增能力单列数据规则、持久化与迁移成本及审批；不补造旧数据的收藏时间或访问历史。

**证据**：`PRD.md:113,243–251`；`ARCHITECTURE.md:65`；`crates/worktwill-core/src/model.rs:87–98`；`crates/worktwill-core/src/store.rs:635–654`。

### 9. 精简工作区入口时保留全部操作目标

对象在侧栏、管理页和时间上下文中重复出现，不一定意味着任务重复。可以减少常驻密度，但不能让不常用工作区失去可达的投放路径。

**建议**：条件采纳收起或“更多”；拖动时仍能访问全部目标，菜单和键盘具备等价路径。动态右栏价值需结合当前上下文核实，不按对象同名直接删除。

**证据**：`PRD.md:102`；`docs/decisions/0025-personal-workbench-sidebar.md:9`；`desktop/src/timeline/ActivityTimeline.tsx:240`。

## 四、补充完整用户闭环与验收

原报告 A01–A18 可以保留，但不能替代既有 F01–F14、U1–U8 及当前阶段要求。

| 补充场景 | 主要通过条件 |
|---|---|
| 不记得名称的旧资料 | 零工作区、无关键词也有可发现的条件查找路径，不只依赖首页少量最近项 |
| 首次授权到首个价值 | 取消→重试→授权→首批结果→搜索→打开，不强制建工作区；读取失败不呈现首次空库 |
| 保存与跨重启取回 | 双工作区＋收藏的同一文件，日常保存、应用关闭期间保存、重启后仍打开正确原件；核对 UUID 与关系 |
| 身份替换与修复 | 同名重建不自动换绑；重新指向展示影响，取消不改关系；确认合并遵循既有契约 |
| 操作影响范围 | 从 A 区移除不影响 B 和收藏；取消收藏不影响关联；删除工作区不影响原件；网页全局删除与单区移除区分 |
| 撤权与迟到结果 | 最后授权撤销后元数据与计数按规则隐藏；有效重叠授权继续可用；旧响应不恢复撤权内容 |
| 键盘与焦点 | 纯键盘可搜索、查看路径、收藏、加入／移出、取消弹窗并返回；中文组字回车不误打开 |
| 聚合与分页 | 若实施聚合，跨页、切时间维度、撤权与身份边界行为稳定，计数含义清晰 |
| 性能与环境 | 按既有规模与候选预算定向测量，记录构建、环境及 P50/P95/P99；Mock、Mac 原生、Windows 分别标记 |

**基本键盘可达、可见焦点和无拖拽替代路径应随相关改造一起回归，不应整体排到 P2。**

本次整改不能弱化正常保存后取回的要求，也不能让“永远报失效但从不误开”替代长期可靠使用。验证限于当前批准的普通本地目录；不重新扩张网络盘、外置盘或同步目录支持。

## 五、建议调整后的顺序

### 第一批：价值明确、风险较低

1. 系统工件统一去噪，覆盖旧库、列表、搜索、动态明细与日历计数。
2. 收藏专页去掉通用 Tab 和无关控制，保留完整操作语义。
3. 搜索补命中解释，复用既有分组、筛选、排序和路径查看能力。
4. 首页调整顺序与密度，保留首次使用、加载、错误和权限状态。
5. 对相关操作做键盘、安全与性能定向回归。

这些是建议优先项，不代表本文授予修改代码的权限。

### 第二批：先确定任务承接，再改导航

1. 确认无关键词条件检索入口与支持的条件。
2. 明确最近资料“查看更多”的落点。
3. 确认工作区快捷入口精简后所有目标仍可达。
4. 用户确认新的信息架构后，承接路径与删入口同批交付。
5. 同步 PRD、架构与验收，避免保留矛盾基线。

### 第三批：有证据再增加

- 时间线短窗口聚合。
- 工作区固定、真实最近访问。
- 收藏时间等新增元数据。
- 视觉精修。

正文索引与内嵌预览不自动进入第三批，仍属于需要独立审批的范围。

现有原件安全、保存后取回、权限与外部拖入的工程收尾要求仍保留。签名发行、用户留存、完整恢复矩阵等继续按现行阶段安排，不因本报告重新升级为 UI 整改前置条件，也不改写未验证状态。

## 六、原报告建议新增的三个部分

### 6.1 决策表

区分：已确认要求、待确认产品变更、建议优化、范围外能力。对每项标记当前证据及批准状态。

### 6.2 任务承接表

逐项回答删入口后，查找、浏览、分页、多选、收藏、加入工作区、定位、修复与返回上下文去哪里完成。不要只证明索引还存在。

### 6.3 状态与验收表

覆盖首次使用、扫描中、读取失败、失联、撤权、身份替换、正常保存重启、取消与删除；将产品用户研究和原生工程验收分开记录。

## 七、最终意见

**保留原报告作为产品诊断稿；补齐上述决策、承接和状态契约后，再转为研发任务单。**

> “去噪、明确页面职责、提高搜索可判断性”方向正确；“搜索足以替代浏览，因此应立即删除所有文件”结论过早。先保证找回与继续工作的完整路径，再决定入口如何收敛。

本汇总未覆盖原报告，未修改 PRD、架构或正式源码；不将静态审查写为产品运行验收通过。源码行号对应审查时版本，后续修改后应重新定位与核实。
