## 2. 总体评价

### 产品层面

首页最近资料、工作区返回，大型快捷搜索、完整结果页，三者职责基本清楚。可以支持查找和继续工作；无需再保留“所有文件”独立页面。静态伙伴和纯文本便签的限制也较克制，没有把它们扩展成任务、提醒或游戏系统。

但这份方案已经超出“三页面换布局”：新增了搜索入口、搜索历史、便签持久化及小组件设置。它们有实际开发和数据维护成本，应明确列为 V1.3 增量，而不是视作已有数据换个位置。

### 架构层面

继续采用 React 管理交互、Rust 管理查询与持久数据、SQLite 保存业务事实的边界，能够承接该方案。无需重写核心、引入新全局 store 或第二套前端检索算法。

主要缺口集中在新增数据生命周期、搜索弹层与结果页的交互状态、真实打开时间返回，以及保存通知对现有查询版本的影响。

### 开发层面

工作包拆分和原生验收意识较好，但部分条款仍把“结构必须采用”与“没有接口可接受”混在一起。应先固定本版实际交付的控制项，再开发，避免按图做完后才发现筛选、跳页、新窗口、批量操作没有对应能力。

**建议有条件采用，不建议原样把提示词作为不需再分析的施工单。以下问题属于规范需要补充的条件，不是要求推翻图稿。**

## 3. 开发前需要补齐的六项关键规则

### R01｜便签是新持久功能，自动保存规则不足

规范 §6.2、NOTE-01～03 已要求创建、编辑、置顶、删除、自动保存、重启与失败重试，但没有定义连续写入、删除期间保存、退出时未保存内容及恢复备份的行为。

典型问题：输入A发起保存，再输入B；A的响应晚到，能否把B标成已保存？用户删除后，旧保存能否重建该便签？“失败后关闭应用再重启能重试”，重试的文本保存在何处？

当前正式 `model.rs`、schema及migration中未见便签业务模型；PRD §8、架构中的note/widget仍为此前范围外内容。新规范可以将其纳入新版本，但必须同步这一范围变化，不能声称只是迁移已有正式便签。

**建议补充：**

- Rust拥有便签UUID、正文、置顶、创建/修改时间和持久提交结果；React持有当前编辑草稿及状态。
- “已保存”只代表该条当前文本版本已提交。旧响应不能把更新的草稿标为已保存或覆盖它。
- 创建重试不重复生成；同条写入有明确顺序；删除与待保存写入不能互相复活。
- 明确最大文本长度、空白条目、置顶并列排序及重复点击处理，不默认无限文本或无限条目无分页。
- 明确退出策略：失败时保留当前草稿并允许重试；若承诺重启后还能重试未确认文本，就必须有可靠的草稿持久化方案。否则只能保证已确认保存内容，退出前应让用户知道未保存状态。
- schema升级、旧库打开、备份/恢复和恢复失败后的数据保持都纳入新增功能测试。当前恢复实现做版本与结构校验，不能只在备份文案中说“包含便签”。
- 当前用户只有一个正式窗口，不必为假设的多用户协作建设完整冲突系统，但必须防本窗口内的连续异步写入错误。

证据：`crates/worktwill-core/src/model.rs:79–117`；`migrations.rs:4`（当前版本8）；`store.rs:1337–1429`（恢复及结构验证）；`PRD.md:252`。

### R02｜便签保存不能不加分析地复用“全资料刷新”

当前资源mutation会增加全局查询revision，并发送 `catalog-changed`；App收到后清空资料、选择和分页。若把每次便签自动保存直接塞进同一路径，可能让用户编辑便签时不断刷新资料列表，并使无关搜索游标失效。

这不是已发生故障，因为便签尚未接入；它是复用现有命令时可以预见的消费链影响。

**建议补充：**先列出便签写入的消费者、通知和版本影响。便签正文变化不应无故失效文件搜索；按现有结构选择有范围的通知/刷新规则，必要时区分领域版本。不要为此预先建设大型事件总线，也不要新建前端正式数据副本。

同理，伙伴隐藏、搜索历史清除等偏好变化，不应默认触发全目录扫描或清空文件结果。

证据：`store.rs:60–62,885`；`src-tauri/src/main.rs:233–249`；`desktop/src/App.tsx:82–90`及catalog事件处理。当前游标携带revision，见 `model.rs:188–203`。

### R03｜空词入口与两种搜索视图，需要明确状态转换

规范 §3.1 和 SR-01 的方向正确：空词可打开页面，但不调用要求1–256字的接口。当前完整搜索在 `view==='search'` 时会提交请求，因此只增加侧栏入口会触发不合法空查询。

另一个更隐蔽的场景：完整页正在查“合同”并有筛选，打开大型快捷搜索输入“招聘”，再按Esc，来源结果页应保留什么？当前两个入口共用query；弹层输入可能直接改变底下完整页查询。这与“不丢来源页上下文”不能同时靠一句“复用同一查询”解决。

**建议补充以下动作表：**

| 动作 | 应发生的事 |
|---|---|
| 侧栏进入空词完整页 | 展示输入与提示，不发空请求，不自动读全库；已有目录授权概览可按需读 |
| 在空词页改类型/日期/工作区 | 保存有效输入条件，但不绕过非空词限制发请求 |
| 完整页清空关键词 | 取消旧page请求，清空旧结果/选择/游标；迟到响应不能恢复旧页 |
| 从完整页打开快捷搜索，再Esc | 恢复或保留来源检索条件；弹层草稿不得无意覆盖来源任务 |
| 弹层点进入完整页 | 提交当前词及兼容条件，清旧选择和游标；明确是否带当前工作区范围 |
| 点击弹层类型 | 由Rust按该类型查询，不只在当前Top30里前端过滤 |
| 弹层中进行关联，取消/完成关联框 | 明确弹层保留/关闭与焦点位置；Esc先关闭最上层，不同时丢两层 |

“共享查询事实源”是复用匹配和权限规则，不要求所有输入框共用一个随时覆盖的文本值。继续由现有App拥有交互状态，区分必要的草稿与已提交条件即可，不必引入路由状态框架。

证据：`App.tsx:139–177,185–209,249–271`。当前quick查询普通模式固定kind为all，完整页跳转重置kind，均需配合新分类行为调整；两条取消lane已存在，应保留。`search.rs:288–303`明确拒绝空词。

### R04｜“最近打开时间”没有现成的行级返回字段

当前最近使用确实按当前对象的opened记录筛选、排序，但最终返回通用Resource DTO；其时间字段只有 `modified_at`。共享列表也始终显示这个字段。

因此，**已有最近打开排序，不等于已有可显示的打开时间**。直接把表头改成“最近打开”，仍渲染mtime，会产生新文案误导。

**建议补充：**首页最近打开列表明确返回真实最后打开时间，或者在没有返回前不显示该列；不能覆盖modified_at的原含义。选择小范围列表DTO或适用的可选字段，先检查消费者，不为这项需求重构全部资源。网页显示“访问”也只能指WorkTwill记录的打开，不代表浏览器访问历史。

证据：`store.rs:294–309`只用MAX(opened.at)排序，`resource_db:242–255`仍读resources.modified_at；`model.rs:87–97`无opened_at；`components.tsx:92`显示modified_at。

### R05｜按图实施的控制项必须有明确取舍清单

规范已禁止假筛选，但 §9 又允许某些时间/工作区筛选缺接口；当前后端其实已有修改日期和单工作区范围。不能把“未查现有能力”写成可接受缺项，也不能因截图出现就把所有控件算进本版。

| 图中能力 | 当前正式能力 | 本版建议 |
|---|---|---|
| 文件/网页/工作区分类 | DTO和查询支持 | 保留；快捷分类向后端传kind |
| 修改日期范围 | search_page支持本地时间边界 | 保留；日期范围名明确为修改日期 |
| 工作区范围 | 支持单个workspace_id | 可接选择器；不能宣称已支持多区组合 |
| 路径或URL前缀 | 已支持字面前缀 | 可保留，不能当可视目录树 |
| PDF/DOCX/图片等格式类别及计数 | 不是现有kind字段的能力 | 本版明确新增或不显示，不做无效可点击控件 |
| 相关性/名称/修改排序 | 已支持 | 复用并评估，不增加假排序 |
| 总数、分类总数 | 现响应只有items/has_more等，无精确total | 使用已返回数或省略；不为仿图强制新增全量count |
| 数字页码、跳第13页、每页10条 | 当前是后端版本化游标/固定批次 | 首版用已有加载更多；不能拿cursor冒充任意跳页 |
| 导出路径、批量打开、网格/详情切换 | 图中出现，工作包未明确完整规则 | 本版先不显示，或单列真实实现和验收 |
| Cmd+Enter“新窗口打开” | 图中出现，当前正式入口只有一个窗口 | 不照抄提示；没有实现就移除该快捷键说明 |
| 组内“查看全部” | 需要带词和对应类别 | 明确组内跳转与全局查看全部区别 |

当前工作区命中可打开，但不作为文件收藏或加入另一个工作区的对象；现ResourceList已禁用工作区复选框。新批量工具栏必须按资源种类处理。混合收藏状态可以用“收藏所选未收藏项”或“取消所选已收藏项”等明确行为，不应根据前端猜测改掉用户未选关系。

同样，跨页分组需明确“同一全局排序的已加载结果按类型展示”，不要顺手改成各组独立分页却还共用一个游标。图中重复的“最佳匹配”与分类项若保留，键盘选中按资源身份保持一致，计数去重。

证据：`model.rs:139–222`；`App.tsx:335–341`；`components.tsx:84–99`；规范 §1.1图A、§1.2图B及 §9。

### R06｜可选历史、必交组件与阶段完成条件需要分清

文档把空间伙伴和便签标P1，同时在UI-01和阻塞问题中要求必须出现。这并非天然矛盾：P1可以表示实施顺序。但必须明确 **V1.3完整交付包含它们**，不能让开发者误读为可省略，也不能把它们追溯成当前040 Mac工程收尾的新阻塞。

搜索历史的状态更模糊：图A和WP03要求历史区，正文又说“如实现”。建议本版若保留此功能，就补：何时记一次、去重、条数/字数上限、存储位置、清除范围及恢复行为；不按每次击键持久化，不把词写入遥测。手动输入的查询词与撤权文件元数据不是同一种数据，需要声明历史策略；无论历史是否保留，重放查询都必须重新检查当前授权，不能缓存旧结果名称路径。

“旧工作区便签迁移”先核对正式库/发布记录。正式源码未见该功能，只在旧设计中出现时，记录无对应正式迁移任务；不为了文档假设建设兼容层或把原型数据自动导入。

提示词要求小提交/MR，而现项目约定Git由用户处理。当前只审查；后续实施应按实际授权决定本地编辑、提交与推送，不让外部提示词自动扩大Git操作范围。

## 4. 可以直接采纳的产品方向

- 大型分栏快捷搜索可做，不必再争论缩成小下拉框；但大型外观不意味着要加载全库或增加结果上限。
- 完整搜索可成为一级入口，空词展示提示而不列全库，与删除“所有文件”可以共存。这是新的访问决定，不是恢复旧总表页。
- 首页两种资料来源与工作区入口清楚，比叠加第二块“继续工作”和整块动态更有边界。
- 静态植物无需生长算法、经验或统计基础设施。用户选择的伙伴与便签可保留为设计目标，不应仅因它们不是文件索引核心而擅自删掉。
- 工件推荐去噪、显式搜索可找回、历史身份与原件只读的规则，比最初统一过滤方案更准确。
- 首页首次价值HOME-04应继续作为产品验收，不要求先建工作区；植物、便签和动画不是首次任务成功的替代证明。

## 5. 布局、资产与真实操作的补充要求

### 最小窗口按当前900×640验收

原生配置当前默认1280×840、最小900×640（`src-tauri/tauri.conf.json:17–20`）。不能只在1512×982对图拍照，也不能为容纳右栏静默提高最小窗口。

侧栏约240、右组件约360再加间距后，900宽不够维持宽阔三列。文档已允许下移/折叠，应具体确定断点：先保障资料操作，右组件下移或可展开；输入便签时不能因容器重挂载丢草稿。英文长文、200%文本/缩放、横向溢出、滚动到全部工作区和搜索底栏都应核查。

### 大型弹层的交互不由图片提供

补焦点限制、背景交互、点击遮罩、重复Cmd/Ctrl+K、最上层Esc、关联弹窗取消、原生确认返回焦点；列表快捷操作不能嵌套成非法交互元素或点击收藏时同时打开文件。

图片上的Cmd+Enter、星标快捷键等，不实现就不展示。组字候选确认不能被搜索或便签自动提交吞掉。

### 素材还不是可直接使用的组件资产

包内只有三张整图。需准备独立植物资源、隐藏/恢复入口与固定配色；不要裁整图充当交互区。静态本地资源适合现CSP，不应为图片引入远端请求、重型动画或前端额外运行时。规范正文说不重复“全部工作区”，参考首页却出现多处入口，应按明文保留一个必要落点，避免机械照图。

“每个工作包至少一张原生截图”可以证明交互外观，但不应强迫无UI的迁移任务拍无信息截图。迁移以数据库/恢复结果为证，最终UI工作包补原生图；未执行的原生矩阵明确登记，不拿组件测试替代。

当前工程清单的040外拖缺口和平台验收保留，不用V1.3新布局绕过；也不将已有证据一律作废。受影响或新缺口重新执行，未改分支引用原记录并标清版本，最终制品运行的是哪套源码必须清楚。

## 8. 最终建议

**采用三张图的设计方向，保留现有技术栈和Rust事实源；先把R01～R06写成明确契约，再进入分包实施。** 最需要防止的不是页面做不出来，而是便签偶发丢字、保存导致文件页抖动、空词页面报错、最近打开显示错误时间，以及按图出现没有真实行为的控件。

无需因此退回旧信息架构、取消用户选择的小组件或引入复杂平台。把便签作为真实新功能交付，把两种搜索作为同一规则下不同交互视图，把每个可见按钮的行为写清，方案就有明确的落地路径。
